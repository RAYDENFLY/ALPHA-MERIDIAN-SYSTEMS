# SignalGenerator — Model B Duplicate Candidates & NOT_SUBMITTED Audit

## Objective

Investigate why the Model B 1H Candidates Pipeline displays eight AGTUSDT LONG candidates, all with `READY` setup status and `NOT_SUBMITTED` execution state.

Determine whether:
1. The same logical setup is being duplicated across scan cycles.
2. Candidates are intentionally not submitted because an execution condition is missing.
3. The paper execution engine is not being invoked.
4. Candidates are rejected or suppressed by risk controls, cooldowns, deduplication, or execution policy without exposing the reason.
5. Liquidity metrics and position quantity are unavailable, stale, or merely not rendered by the UI.

This is a diagnostic and minimal-remediation task. Do not assume a bug before tracing the actual code path.

## Strict Constraints

- Model A remains completely frozen, including strategy, 11-symbol whitelist, risk policy, historical journals, and forward cohort.
- Model C remains deferred.
- Preserve `SCANNER_MODE=PAPER` and `live_trading_locked=True`.
- Never submit, modify, or cancel live exchange orders.
- Preserve Model B's independent $100 paper equity, $1 target risk, $15 margin cap, $3 daily cap, $7.50 weekly cap, and maximum three concurrent positions.
- Do not fabricate fills, orders, trades, or execution events.
- Do not loosen strategy filters or risk controls merely to generate more entries.
- Preserve existing databases and historical records.

## Phase 1 — Trace the Eight Candidates

Inspect the actual records behind the displayed candidates.

For each record, retrieve:
- Candidate ID and stable setup ID.
- Model ID.
- Symbol and direction.
- Creation and last-update timestamps.
- Scan-cycle ID or source timestamp, if available.
- Entry, SL, TP1, and TP2.
- Strategy/setup type.
- Execution state and state-transition history.
- Engine evidence and rejection reasons.
- Whether a corresponding paper order, position, or trade exists.

Determine whether the eight rows represent:
- Eight distinct valid setups.
- Repeated snapshots of the same setup across scans.
- Different candidate IDs for one logical setup.
- Historical stale candidates that should no longer appear as current.
- A mixture of the above.

Do not infer uniqueness from candidate IDs alone. Identify the correct logical deduplication key and its intended lifetime.

## Phase 2 — Trace the Execution Lifecycle

Trace one representative READY candidate through:

`Candidate Generation → Validation → Risk Approval → Paper Order Submission → Fill Evaluation → Position Creation → Journal`

Inspect `ModelBRunner.run_scan_cycle()`, `ModelBStrategyGenerator`, risk checks, `PaperExecutionEngine`, persistence logic, and the dashboard/API.

For every stage, record:
- Whether it was invoked.
- Its result.
- Whether the candidate advanced to the next stage.
- The exact reason for any rejection, suppression, or wait state.

Verify whether `READY` is intended to mean setup-valid or execution-approved. Keep these states separate.

If submission is intentionally delayed until a price trigger or another condition occurs, expose that condition and the relevant trigger price.

## Phase 3 — Fix Candidate Deduplication

If repeated rows represent the same logical setup:

1. Implement or correct idempotent candidate upsert behavior using a defensible logical setup identity.
2. Prevent repeated scan cycles from creating duplicate active candidates.
3. Preserve legitimate new setups after the prior setup expires, is invalidated, or a genuinely new setup forms.
4. Keep historical state transitions auditable.
5. Avoid creating multiple paper orders or positions for the same logical setup.
6. Ensure deduplication works across application restarts.

Do not delete historical records simply to make the dashboard display fewer rows.

## Phase 4 — Explain Execution State

Expose truthful execution states, reusing existing lifecycle conventions where possible:

- `NOT_SUBMITTED`: no paper order has been submitted.
- `ENTRY_PENDING`: a paper order exists and awaits its defined fill conditions.
- `OPEN`: a simulated fill has created a persisted position.
- `CLOSED`: the position has been closed and the trade journaled.
- `REJECTED`, `EXPIRED`, `CANCELLED`, `ERROR`: use when supported by actual lifecycle evidence.

For `NOT_SUBMITTED`, display a structured reason where possible, such as:
- Waiting for entry trigger.
- Risk validation pending.
- Missing required market data.
- Execution engine not invoked.
- Submission suppressed by deduplication.
- Candidate expired or invalidated.
- Unknown reason requiring investigation.

Do not assign a reason without evidence.

## Phase 5 — Audit Missing Metrics

Investigate why the screenshot displays `Spread: --`, `Depth Imb: --`, `CVD: --`, and `Qty: --`.

Determine whether each value is:
- Not collected.
- Unavailable from the venue.
- Stale.
- Rejected by validation.
- Missing from the API response.
- Lost during frontend rendering.
- Not applicable at the current lifecycle stage.

Display explicit unavailable states and timestamps rather than silently presenting missing values as valid neutral readings.

If quantity cannot be calculated because risk or entry validation has not completed, state that explicitly.

## Phase 6 — Tests

Add deterministic tests for:
1. Repeated scan cycles do not create duplicate active candidates for one logical setup.
2. A genuinely new setup can be created after invalidation or expiration.
3. Candidate persistence survives restart without duplicate active rows.
4. READY alone does not create a paper order or position.
5. A valid candidate advances through the intended submission path when all required conditions are satisfied.
6. Risk rejection and missing-data rejection expose explicit reasons.
7. Paper orders and positions remain idempotent.
8. Dashboard rows and execution states match API and database records.
9. Model A regression tests and historical cohort data remain unchanged.
10. Live trading remains locked.

Run focused tests and the full test suite. Report exact results, warnings, and failures.
